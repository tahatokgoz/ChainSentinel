# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Common Commands

Install dependencies and run the web app:
```bash
pip install -r requirements.txt
uvicorn backend.main:app --host 0.0.0.0 --port 9000
```
The frontend (single-page `frontend/index.html`) and the API are served by the same FastAPI process. The UI is at `http://localhost:9000/`, the API under `/api/...`, and generated PDFs under `/reports-static/...`.

CLI (uses the same scanners/DB as the web app):
```bash
python cli.py scan iot|portal|api|all [--host HOST] [--report]
python cli.py report <scan_id>
python cli.py lab status
```

Vulnerable lab targets (only built when running locally; `lab/` is gitignored):
```bash
docker compose -f lab/docker-compose.yml up -d   # iot:9081, portal:9082, api:9083, mqtt:1883
```

MCP server (Claude Desktop integration — backend must already be running on :9000):
```bash
python mcp_server/server.py
```

There is no test suite, linter, or build step configured. `chainsentinel.db` (SQLite) is created automatically on first run via `init_db()` in the FastAPI lifespan.

## Architecture

ChainSentinel is a security-testing tool with **three entry points that all share the same scanner + DB layer**: the FastAPI web app (`backend/main.py`), the CLI (`cli.py`), and the MCP server (`mcp_server/server.py`, which calls the FastAPI HTTP API rather than importing the scanners directly). Keep this in mind: a change to scanner output shape or DB models affects all three.

### Request → scan → finding flow

1. `POST /api/scans` (or `/api/discovery/auto-scan`) creates a `Scan` row and **spawns a `threading.Thread`** running `backend.services.scan_runner.run_scan` with its own `SessionLocal()`. The HTTP request returns immediately while the scan runs in the background — clients poll `GET /api/scans/{id}` for status (`pending` → `running` → `completed`/`failed`).
2. `scan_runner.run_scan` looks up the scenario in `SCANNER_MAP` (`iot`/`portal`/`api`), reachability-checks the target, then calls `scanner.run()`. **It also unconditionally appends results from `MQTTScanner` and `ProtocolScanner`** for every scan, regardless of scenario — this is intentional, not a bug.
3. Each scanner inherits `scanners.base.BaseScanner` and returns a list of finding dicts via `add_finding(...)`. The runner persists them as `Finding` rows linked to the `Scan`.

When adding a new scanner: subclass `BaseScanner`, register it in `SCANNER_MAP` if it's a primary scenario, or call it directly from `run_scan` if it should run alongside every scan (like MQTT/Protocol).

### AI provider layer

`ai_providers/` follows a strict plugin pattern: each provider subclasses `BaseAIProvider` and exposes a module-level `SETUP_GUIDE` string. `backend/routers/ai.py` resolves providers via `PROVIDER_MAP` + `importlib.import_module` — so adding a provider means (a) creating `ai_providers/<name>_provider.py` with the class and `SETUP_GUIDE`, (b) adding entries to `PROVIDER_MAP` and `DEFAULT_MODELS` in `routers/ai.py`. The shared prompt and JSON-fence-stripping parser live in `BaseAIProvider._build_prompt` / `_parse_response`; the JSON schema returned to the frontend (risk_summary, executive_summary, attack_chains, prioritization, mitre_mapping) is fixed by that prompt.

**AI settings are stored in a module-level dict** (`ai_settings` in `routers/ai.py`), not the database — they reset on server restart. Analysis results, however, are cached in the `AIAnalysis` table per scan; calling `/api/ai/analyze/{scan_id}` a second time returns the cached row.

### Network discovery

`scanners/network_discovery.py` requires the system `nmap` binary plus `python-nmap`. `get_local_network()` auto-detects the LAN by opening a UDP socket to 8.8.8.8 — no traffic is sent, but it requires network egress. Discovery classifies hosts (IoT / web portal / API) by inspecting open ports, and `/api/discovery/auto-scan` maps those categories back to the `iot`/`portal`/`api` scenarios.

### Frontend

`frontend/index.html` is a single self-contained HTML file (Tailwind via CDN, Chart.js) that talks only to `/api/...`. There is no build step or framework — edit the file directly.

### Config

All runtime config flows through `backend/config.py` (loaded from `.env` via `python-dotenv`). `BASE_DIR` and `REPORTS_DIR` are derived from the file's location, so the app must be launched from the project root for the static-file mounts (`/`, `/reports-static`) to resolve.

## Notes

- `lab/` is in `.gitignore` — the vulnerable test apps are not part of the repo's tracked source. Treat them as a local dev convenience.
- Reports are PDFs generated by `backend/services/report_generator.py` (ReportLab) and written to `reports/` (also gitignored).
- This tool performs active exploitation (SQLi, command injection, default-credential brute force, etc.). Only run scans against hosts you own or are explicitly authorized to test.

## Rules for Claude

- Respond to me in Turkish, but keep code and commit messages in English
- Before writing any new feature, produce a plan first, wait for approval, then write code
- When adding a new scanner: subclass `BaseScanner`, register in `SCANNER_MAP`, never return dummy data — it must actually scan
- When adding a new AI provider: create `ai_providers/<name>_provider.py` with the class and `SETUP_GUIDE`, then update `PROVIDER_MAP` and `DEFAULT_MODELS` in `routers/ai.py` — all four, don't skip any
- Do not change the AI response JSON schema (risk_summary, executive_summary, attack_chains, prioritization, mitre_mapping) — the frontend depends on it
- Do not touch `lab/` — it's gitignored on purpose
- This tool performs active exploitation — always note in comments that code is intended only for authorized test environments

## Do not

- Do not delete `chainsentinel.db` — there are no migrations
- If suggesting to move `ai_settings` dict to the database, ask first
- Do not add heavy ML libraries (torch, tensorflow, etc.) to requirements.txt — this tool must stay lightweight
